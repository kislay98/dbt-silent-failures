# Ground truth: rename_and_new_status

**What broke:** `cases/rename_and_new_status/inject.py` applies two changes to `jaffle_shop/seeds/raw_orders.csv` in
one migration. From 1 March 2018 the orders feed writes `order_status` and leaves `status` empty (`order_status`
backfilled for all 99 rows; `status` blank on the 43 orders 57 to 99, as in `status_renamed`). From 10 March the new
fulfilment flow writes `delivered` where the app used to write `completed`, in the new column only: orders 66, 67,
68, 69, 70, 73, 75 and 76 (136.00). No schema file was widened, because the value never reached a test.

**Where it shows:** `stg_orders` still reads `status`, so it is NULL for every order from 1 March and
`customers.completed_lifetime_value` stops counting them: 824.00 instead of 1103.00, March at 0 instead of 279.00.
Customer 3 falls from 65.00 to 46.00, customer 36 to 0. The `delivered` orders hide behind the NULLs: reading the new
column alone brings completed revenue to 967.00, not 1103.00, and makes both `accepted_values` tests fail on
`delivered`. `orders.amount`, `daily_revenue` and `region_revenue` are unchanged.

**Why nothing fails:** every dbt test still passes (44/44): `accepted_values` ignores NULL, nothing tests `not_null`
on status, and `delivered` sits in a column no model reads.

**How the output changes:**

| Measure | Clean | Broken |
|---|---|---|
| `sum(completed_lifetime_value)` from `customers` | 1103.0 | 824.0 |
| `orders` with NULL `status` | 0 | 43 (ids 57 to 99, 761.0) |
| `orders` by status | completed 67 (1103.0), placed 13, shipped 13, return_pending 2, returned 4 | completed 50 (824.0), return_pending 2, returned 4, NULL 43 |
| `completed_lifetime_value` for customers 3, 8, 19, 36, 53, 79 | 65.0, 45.0, 3.0, 28.0, 39.0, 27.0 | 46.0, 19.0, 0.0, 0.0, 23.0, 4.0 |
| `raw_orders.order_status` on the 43 blank-status rows | column absent | completed 9, delivered 8, placed 13, shipped 13 |
| `sum(amount)` from `orders`, `sum(revenue)` from `daily_revenue` | 1672.0, 1672.0 | unchanged |

**Key number:** `select round(sum(completed_lifetime_value), 2) from customers` is 1103.0 clean and 824.0 broken (checked by `check_case.py`).

**Correct fix:** both changes, or the output stays wrong: read the new column (`coalesce(status, order_status)` in
`stg_orders`, or the feed restored) and count `delivered` as completed (map it to `completed` in staging, or widen the
filter in `customers`; if the value is kept, add it to both `accepted_values` lists or the build goes red). The rename
alone gives 967.00 and a failing test; the status alone changes nothing while `status` is NULL. Guards: `not_null` on
`stg_orders.status`, `accepted_values` kept strict (it catches `delivered` as soon as the column is read), and a
reconciliation of completed revenue to the admin.

## Response

## 1. Root cause

`stg_orders.sql` maps `status` from `raw_orders.status`, but the warehouse's `raw_orders` now also has an `order_status` column. The `status` column is NULL for 43 of the 99 orders, so those orders reach `orders`, `customers`, and every downstream model with no status.

The numbers fit:

- `orders` has 50 completed orders worth 824.00, 43 orders with NULL status worth 761.00, and 6 others worth 87.00. That totals 1672.00, matching `sum(orders.amount)`.
- Last week's 1103.00 minus today's 824.00 is 279.00, which is the March completed revenue the admin shows. Those orders are almost certainly in the NULL-status group.
- `customers.customer_lifetime_value` (1672.00) is built from payments, not status, so it is unaffected. Only the completed figures drop.
- The `raw_orders` sample shows the pattern: rows with `status = NULL` and `order_status = 'placed'` or `'delivered'`, and rows where both are `'completed'`.

Why the tests passed: `accepted_values` ignores NULLs, and nothing tests `stg_orders.status` or `orders.status` for `not_null`. A NULL status passes every test in the project.

The change happened in the source, not in the dbt code. I'm inferring that from the fact that last week's number was correct and the models have not changed. The ingestion job's schema change is the likely trigger; I can't see its history to confirm.

Two side notes:

- The log says "32 data tests" were found but "28" ran. The 4 missing are almost certainly the `not_null` tests on `raw_customer_regions` and `raw_payment_methods`, because the seeds are not part of this build. Those tests have never run in the nightly job.
- `customers` documents a `total_order_amount` column that does not exist. It's documentation drift, not the cause.

## 2. Fix

Confirm first which column is authoritative and what `'delivered'` means. Then run this in the warehouse:

```sql
select order_status, count(*), round(sum(amount), 2)
from orders o
join raw_orders r on r.id = o.order_id
where status is null
group by 1;
```

If the `'completed'` rows sum to 279.00 and the existing 50 completed orders plus those give 1103.00, then `order_status` is the right source and `'delivered'` is not counted as completed. In that case, fix staging:

```sql
-- stg_orders.sql
renamed as (

    select
        id as order_id,
        user_id as customer_id,
        ordered_at,
        cast(ordered_at as date) as order_date,
        coalesce(status, order_status) as status

    from source

)
```

If `'delivered'` rows should count as completed, add a mapping for it. Confirm the business rule with finance before choosing. Once `'delivered'` is in the status column, the existing `accepted_values` test will fail on it, which is the test working as intended.

Then rebuild `stg_orders`, `orders`, `customers`, and `region_revenue`. `dbt build --select stg_orders+` will do it.

## 3. A test that would have caught it

Add `not_null` to `status` on both the staging and mart models. `accepted_values` alone can't catch NULLs:

```yaml
# models/staging/schema.yml
  - name: stg_orders
    columns:
      - name: status
        tests:
          - not_null
          - accepted_values:
              arguments:
                values: ['placed', 'shipped', 'completed', 'return_pending', 'returned']
```

```yaml
# models/schema.yml, under orders.columns
      - name: status
        tests:
          - not_null
          - accepted_values:
              arguments:
                values: ['placed', 'shipped', 'completed', 'return_pending', 'returned']
```

For a stronger guard, add a singular test that fails if the staging status differs from the source's `order_status`. Also add the seed-based tests to the nightly run, so the 4 missing tests execute.
