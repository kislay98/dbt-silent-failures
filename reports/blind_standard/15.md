# Ground truth: fanout_and_late

**What broke:** `cases/fanout_and_late/inject.py` appends six February orders (ids 100 to 105 for customers 2, 15, 28,
41, 60 and 77, all `completed`, 65.00 in all) to `jaffle_shop/seeds/raw_orders.csv` and their payments (ids 114 to 119)
to `jaffle_shop/seeds/raw_payments.csv`, as in `late_orders`; and it appends the region rows of those six customers to
`jaffle_shop/seeds/raw_customer_regions.csv` again, same region, `updated_at` 2018-04-02, as in `region_fanout`: the
store's sync re-sent its customer records with the backfill and the loader appended them.

**Where it shows:** `orders`, `customers` and `region_revenue` pick the six orders up (105 orders, 1737.00, February
33 orders and 480.00). `daily_revenue` is incremental and rebuilds the last three days only, so it keeps 99 orders,
1672.00 and 27 orders, 415.00 for February; six days disagree between the two models (3, 8, 13, 17, 22 and 26
February). `region_revenue` joins the regions feed before it aggregates, so every payment of the six customers is
summed twice: 1838.00 instead of 1737.00 (NSW 394.00 instead of 349.00, QLD 377.00 instead of 356.00, VIC 446.00
instead of 411.00), while the distinct customer and order counts per region are right. The two defects pull the same
way: the regional report is 101.00 over `orders`, and `orders` is 65.00 over the dashboard.

**Why nothing fails:** every dbt test still passes (44/44): the orders and payments have fresh ids, the regions seed is
tested `not_null` and not `unique`, `region_revenue.region` stays unique after the `group by`, and nothing compares
`daily_revenue` or `region_revenue` to `orders`.

**Correct fix:** both changes, or the output stays wrong. `daily_revenue` needs a full refresh and a strategy that
survives late rows (rebuild every day present in the new source rows, key the window on a load timestamp, or make it a
table); and `region_revenue` needs one region row per customer (the latest `updated_at`, or distinct customer and
region, or the loader upserting on the key). The refresh alone leaves the regional report at 1838.00; one row per
customer alone leaves the dashboard at 1672.00; restoring the seeds removes six real orders. Guards: a per-day
reconciliation of `daily_revenue` to `orders`, `unique` on `raw_customer_regions.customer_id` (or a test that
`sum(region_revenue.revenue)` equals `sum(orders.amount)`).

## Response

## 1. Root cause

`models/daily_revenue.sql`: the incremental filter is keyed on the order date, not on when the data arrived:

```sql
where order_date >= (select max(order_date) - interval 3 day from {{ this }})
```

On each run it only recomputes the last 3 days before the table's latest `order_date` (early April here). The model assumes late data lands "a day or two after the order". The backfill from the store whose sync was down is different: it arrived last night carrying February order dates.

- `orders` is a full-rebuild table, so it picked up the six completed orders and shows 33 orders / 480.00 for February.
- `daily_revenue` never re-aggregated those February days, so it still shows 27 / 415.00.
- The gap is exactly 6 orders and 65.00, which matches the backfill.

All tests pass because none of them compares the two models. `unique` and `not_null` on `daily_revenue` are satisfied by a stale table.

## 2. Fix

Immediate data fix, rebuilding the table from `orders`:

```
dbt build --full-refresh -s daily_revenue
```

Durable fix: with about 100 orders there's no reason to be incremental, and any fixed lookback will break on the next large backfill. Make it a plain table in `daily_revenue.sql`:

```sql
{{ config(materialized='table') }}

with orders as (

    select * from {{ ref('orders') }}

),

final as (

    select
        order_date,
        count(*) as orders,
        sum(amount) as revenue

    from orders
    group by order_date

)

select * from final
```

If the model has to stay incremental at larger volume, the window needs to key on load time (for example an `_loaded_at` column on the raw tables). `order_date` can't detect late arrivals. A periodic `--full-refresh` would also be needed.

## 3. Test that would have caught it

A singular test, `tests/assert_daily_revenue_matches_orders.sql`, that reconciles the two models per day:

```sql
with o as (

    select order_date, count(*) as orders, sum(amount) as revenue
    from {{ ref('orders') }}
    group by order_date

)

select
    coalesce(o.order_date, d.order_date) as order_date,
    o.orders as expected_orders,
    d.orders as actual_orders,
    o.revenue as expected_revenue,
    d.revenue as actual_revenue

from o
full outer join {{ ref('daily_revenue') }} as d
    on o.order_date = d.order_date

where o.orders is distinct from d.orders
   or round(o.revenue, 2) is distinct from round(d.revenue, 2)
```

Last night it would have returned the February days with the missing orders and failed the build.

## Separate bug in the output

`region_revenue` totals 1,838.00, but total order amount is 1,737.00. `raw_customer_regions` has 106 rows for 100 customers (it carries `updated_at`), so some customers have multiple region rows. The `join regions` fans out and double-counts their payments. That model should dedupe to the latest row per `customer_id`, and the `raw_customer_regions.customer_id` column should get a `unique` test (which currently only has `not_null`).
